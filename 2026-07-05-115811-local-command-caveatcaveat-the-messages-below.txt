  持久化、主从复制、哨兵等内容），跟 Docker 完全不相关。

  LLM 行为： LLM 用自己的知识正确回答了 Docker CI/CD
  的问题，但同时引用了不相关的 Redis 文档块作为"证据"。

  根因分析：

  1. 知识路由没有最低分数阈值：confidence=1.0 表示路由认为 Redis
  文档是"完美匹配"，实际上 semantic 分数只有 11.71（很低），但因为 +scopeMatch 
  +relation 两个加成直接把总分拉到了 45.71
  2. 只有一个文档时，任何问题都会被路由到它：没有 Docker 文档，semantic 搜索把
  "docker" 和 "middleware/redis"
  做了语义关联（确实都属于后端技术栈），但这明显是错误匹配
  3. 缺少"无匹配文档"的兜底策略：当 semantic 分数低于某个阈值时，应该退化为
  OPEN_CHAT 模式（不检索文档，用 LLM 自身知识回答），而不是强行匹配到唯一的文档
  4. query rewrite 没有生效：改写后的问题和原始问题完全一样（"docker的ci c
  d"），说明改写服务没有对输入做任何处理

  建议修复方向：

  - AUTO_DOCUMENT 模式增加 semantic score 最低阈值（如 < 15 分时退化为
  OPEN_CHAT）
  - 路由时检查 top document 的 raw semantic score 是否足够高，不能仅靠
  scope/topic 加成
  - 当 top_documents 中 semantic
  分数太低时，不自动选择文档，改为告知用户"未找到相关文档，将以通用模式回答"
