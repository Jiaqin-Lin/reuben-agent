# Reuben-Agent 项目亮点逐字稿

> 面试用，每个亮点独立成章。结构：**问题 → 如果不管会怎样 → 我的方案 → 核心细节 → 效果**。
> 可按 STAR 原则展开：Situation → Task → Action → Result。

## 亮点 1：文档结构提取管线（4 阶段 + 16 级信号分类 + LLM 消解歧义）

### 问题背景

文档上传后第一步是提取纯文本。不同格式处理完的结果差异很大：

- **Markdown/TXT 文件**：直接 UTF-8 解码，原始格式标记（`#`、`- `、缩进）都在，结构信息基本保留
- **PDF/Word/HTML 文件**：经过 Apache Tika 提取后，所有排版信息全丢了——标题的加粗变大没了、段落的缩进没了、列表的项目符号变成了普通字符。你拿到的就是一坨换行符分隔的裸文字

但不管你拿到的是哪种，最终要做的是同一件事：**在这坨文字里重建文档的结构骨架**——哪些行是标题、哪一级标题、哪些行属于同一个列表、哪些行是正文。而且真实世界的文档格式极其不规范——有人用加粗代替标题层级、有人的编号是跳的（1.1 直接到 1.1.3）、有人把一整段正文写成了短句堆叠看起来很像个标题。

### 如果不管（两种常见做法，各有一屁股问题）

**做法 A：跳过结构提取，直接固定窗口切块。** 这是大多数 Demo 的做法——拿 RecursiveCharacterTextSplitter，设个 chunk_size=1000，不管文档里有什么结构，按字符数一刀一刀切。后果很直接：一篇 50 条的合同，用户搜"第 35 条 违约责任"，召回的 chunk 可能是第 34 条后半段 + 第 35 条前半段 + 第 36 条开头——窗口恰好卡在中间。LLM 看到的证据是残的，回答质量断崖式下降。更隐蔽的问题是：同一个条款的两个段落被切进两个不同的 chunk，检索时 A 段召回率高 B 段召回率低，LLM 只看到半截条款就开始编答案。

**做法 B：全部交给 LLM 提取结构。** 这是另一个极端——既然 LLM 理解能力强，那把全文扔给它，让它一次性标出所有标题和层级。实际跑起来三个致命伤：第一，200 页的合同，token 量远超上下文窗口，得分段送——分段本身就是一种隐式的"切块"，第一段末尾和第二段开头的结构关系就断了，LLM 连上下文都看不到怎么判断结构连续性？第二，LLM 会"创作"——在一个没有标题的纯叙述段落里，LLM 可能觉得"这里应该有个标题"，凭空给你造一个；第三，同一个文档送两次，LLM 可能给出不同的结构判定——因为采样温度的随机性，这一次判为标题的行下一次可能判为正文，这对企业场景是不可接受的——你总不希望同一份合同今天搜"第五章"能命中，明天同一个问题命中不了吧。

所以纯规则覆盖不全（格式千变万化，规则总有盲区），纯 LLM 又贵又飘（成本高、不稳定、长文档窗口不够）。关键问题是**怎么把两者的长处结合起来**。

### 我的方案

四阶段管线，核心思想是：**像漏斗一样逐步筛选——先用规则引擎把 90% 置信度高的行直接判掉，只把中间态（规则吃不准的 5-10%）交给 LLM 做最终裁决。规则提供速度、稳定性和零成本，LLM 填补规则的盲区。**

**Stage 1 — 信号提取（Signal Extractor）**

先把裸文字按逻辑行分割。有一个常见坑：Word 里排成列表格式的"1. 概述  2. 范围  3. 定义"，Tika 提取后可能被压成一行。我用正则 lookahead 提前展开这些被压缩的多行，避免后续处理漏掉条目。

然后对每一行做 16 级优先级的逐行分类。所谓优先级，就是从最明确的信号开始往下匹配，匹配到就停。从高到低大致是：

```
P1-P3:  Markdown 标题标记 (### / ## / #)
        中文标准章节号 ("第一章" / "第二节")
        十进制层级编号 ("1.1" / "3.2.5")
        → HEADING, confidence 0.95+

P4-P6:  编号+空格开头的短行
        全大写短行、括号编号
        → HEADING, confidence 0.80-0.95

P7-P8:  短句、看起来像标题但不太确定
        → HEADING_CANDIDATE, confidence 0.45-0.80  ← 关键！这是后面送 LLM 的

P9-P12: 列表项 (bullet -/*、checkbox、ordered 1. 2. 3.)
        引用行 (> 开头)、表格残留行
        → LIST_ITEM / QUOTE / TABLE_ROW, confidence 0.70-0.90

P13-P14: 步骤描述条目、正文段落
         → STEP_ITEM / BODY, confidence 0.70+

P15-P16: 空行、重复噪音（页眉页脚、版权行、版本号）
         → BLANK / NOISE, confidence 0.90+
```

关键设计：**Markdown 标题和"第一章"这种明确模式放最高优先级**。因为对于 MD/TXT 文件，`##` 就是铁证如山的标题标记，不需要怀疑。对于 PDF/Word 文件，虽然没有 Markdown 标记，但"第一章""1.1.3"这类编号模式同样高度可靠。只有编号不存在、长度模棱两可的短行，才会掉进 P7-P8 变成 CANDIDATE。

同时做了 O(n) 双遍上下文计算——预计算每行的前一个非空行和后一个非空行，注入到信号里。比如一行"1.1 概述"，如果它在 Markdown 里（有格式标记），光靠标记就够了；但如果它是从 PDF 提取的（标记丢了），仅靠内容"1.1 概述"判标题可能有风险——万一是正文里引用了某个章节号呢？这时候上下文就起作用了：如果它下面紧跟着"1.2 背景"，那它几乎肯定是标题，confidence 可以拉高；如果下面是一段连续正文，那就该降级为 CANDIDATE，让 LLM 去看。

**Stage 2 — 歧义消解（Ambiguity Resolver）**

这里只处理 Stage 1 标注为 HEADING_CANDIDATE 的行——那些 confidence 落在 0.45 到 0.80 之间的模糊信号。

高于 0.80 的行（P1-P6），规则引擎已经有足够把握了——Markdown `###`、"第一章"、"3.2.5"这种模式，判断错误的概率极低，不需要额外验证，直接接受。低于 0.45 的行（P9-P16），规则引擎也足够确信它们不是标题——list item 有 bullet 标记、正文是长段落、空行和噪音更不可能误解——同样不需要 LLM。

**只有中间态才送 LLM**。为什么这是正确的策略？因为规则引擎在两个极端（明显是标题、明显不是标题）的判断准确率极高——这些 case 规则的特征是结构化的、确定的。出问题的永远是模棱两可的中间 case——一条 6 个字的短行，没有编号前缀，前后都是正文。这种 case 规则给不了高分也下不了定论，恰好适合 LLM——LLM 的强项就是利用上下文语义做判断，而这类模糊信号通常量很少（200 页文档 5000 行，HEADING_CANDIDATE 通常只有 20-50 行）。

送 LLM 时做了两个控制：一次最多送 8 个信号（maxAmbiguousSignalsPerCall=8），每个信号附上前后各 4 行的上下文窗口（contextWindowLines=4），让 LLM 在充足上下文中判定到底是 HEADING、LIST_ITEM 还是 BODY。LLM 的判定结果覆盖 Stage 1 的原始标注。

还有一个总开关 `llmDisambiguationEnabled`——关闭后管线零 LLM 调用，纯规则跑。给用户选择权：如果你处理的文档格式都很规范，规则引擎就够了，不需要多花 token；如果你的文档格式很野，打开开关让 LLM 帮你兜底。

**Stage 3 — 层级解析（Hierarchy Resolver）**

每行的标签确定后，把扁平的信号列表构建成树形结构：确定每个标题的嵌套深度（是第几级标题）、它的子节点有哪些、它挂在哪个父标题下面。核心逻辑是通过标题的编号模式推断层级——"1.2" 是 "1" 的子节点，"1.2.3" 是 "1.2" 的子节点。

**Stage 4 — 树验证（Tree Validator）**

六步修复验证，处理前面各阶段遗留的边界问题：

- **重建兄弟链接**（prevSibling/nextSibling 关系）。Stage 3 产出的树有父子关系但没有兄弟关系——比如同一个父节点下的三个子节点，你知道它们同级，但不知道谁在谁前谁在后。这一步按原始文档中的出现顺序给同级节点建立前后链接。为什么要存这个？因为后续图导航查询"上一节/下一节"时，直接读 prevSiblingId/nextSiblingId 就够了，不需要实时排序

- **规范化路径（canonical path）**。原始文档的编号可能不连续（1.1 直接跳到 1.1.3）、可能重复（第 3 页和第 15 页各有一个"2.1"）、可能深度跳级（一个 depth=4 的节点父节点 depth=2，中间缺了一级）。规范化就是给每个节点分配一个**在结构树中唯一且确定的位置标识**，比如 `1 > 1.1 > 1.1.2`——不管原始编号怎么写的，这个路径标识了它"从根节点到当前节点怎么走"。后续检索时按这个路径过滤，不会因为编号混乱而漏掉或重复

- **合并重复标题**：同一个标题文本在文档中出现了两次——只保留第一个节点，第二次出现的作为重复节点合并到前一个的子树里

- **修正深度跳级**：编号从 1.1 直接跳到 1.1.1.1，中间没有 1.1.1——补一个占位节点，保证树结构的父子链完整不中断

### 文档质量评估（解析管线产出，策略推荐的输入）

四阶段结构提取完成后，顺便算了一组质量指标——不需要额外步骤，数据都在手边。这些指标是亮点 2 策略推荐引擎的决策依据：

- **标题数量（headingCount）**：树里深度 > 0 的 CHAPTER 节点数。标题越多文档骨架越清晰，倾向于用 STRUCTURE 策略
- **段落数量（paragraphCount）**：按双换行分割纯文本后的段落数。段落太少说明文档可能是表格或列表为主，不适合语义切
- **Token 估算（tokenEstimate）**：不是调 tokenizer（那样太慢），而是用经验公式——中文字符 1 token/字，英文单词 1 token/词，其他 1 token/4 字符。这个估算是为了判断 LLM 策略是否可行——LLM 有上下文窗口限制，token 量超了就跳过这个选项
- **结构层级（structureLevel）**：三段式评级——高（≥5 个标题）、中（≥2 个标题）、低（≥3 个段落）、未知（其余）。评级高的文档优先走 STRUCTURE 管道
- **内容质量（contentQuality）**：通过 Unicode 替换字符 `U+FFFD` 的占比来量化。Tika 在遇到无法解码的字符时会用 `�`（U+FFFD）替代——如果一份文档里这个字符的比例 > 2%，大概率是 OCR 产物或者编码损坏的 PDF，质量判低；如果 < 0.5%，说明文本干净，质量判高。这个分数决定了要不要启用 LLM 切块——脏文本规则切不准，恰好是 LLM 的用武之地

这五个指标不是拍脑袋算的——它们直接决定了下一阶段（策略推荐）的三元决策：**用什么 Parent 管道、用什么 Child 管道、要不要上 LLM**。

### 核心细节

- **16 个优先级的顺序为什么以 HEADING 开头？** 因为标题是结构骨架，骨架错了后面层级解析、子节点归属全错。宁可把一个 BODY 误判成 HEADING（进了 Stage 2 还可以被 LLM 纠正，或者 Stage 4 修复时发现它没有子节点而降级），也绝不能把一个 HEADING 漏判成 BODY（漏了就彻底没了，后面无法恢复）
- **为什么 Stage 2 一次只送 8 个而不是全部一起送？** 限制窗口大小是为了控制 LLM 调用的 token 消耗——8 个信号 ×（1 行 + 4 行上文 + 4 行下文）≈ 72 行文本，加上 prompt 模板大约 2000-3000 token，单次调用可控。如果模糊信号超过 8 个（极少数大文档），分多批送
- **上下文窗口为什么是 4 行？** 做实验调出来的——2 行太短，标题和它下面第一个子标题之间如果隔了 3 行正文，2 行窗口看不到；6 行和 4 行准确率几乎一样，但 6 行多消耗 50% token。4 行是边际收益的拐点

### 效果

- 规则引擎直接覆盖约 90% 的行（P1-P6 明确标题 + P9-P16 明确非标题），零 LLM 调用
- 只有 5-10% 的行落入 CANDIDATE 区间，需要 LLM 判定
- LLM 调用量相比"全部送 LLM"减少 90%，且每次调用是小批量的精准判定而非全文处理
- 关闭 LLM 消解后（`llmDisambiguationEnabled=false`），整个管线零模型依赖，适合离线批量处理或成本敏感场景

### 如果面试官追问

> "16 个优先级要维护很多规则，为什么不直接用 LLM 一次性提取全部结构？"

三个核心原因。第一，上下文窗口——200+ 页文档 token 量远超窗口，得分段送，分段本身就切断了跨段的结构连续性，LLM 看不到全局反而容易错；第二，稳定性——LLM 是非确定性的，同一份文档送两次可能给出不同的结构判定，这在你搜索"第五章"时就是灾难；第三，成本——每份文档全量 LLM 处理，按量计费的数字会很难看。规则引擎虽然需要手工维护 16 条规则，但它是确定性的、零延迟的、零成本的，而且一旦写对就永久有效。你可以把 LLM 想象成医院的专家号——常见病全科医生（规则引擎）直接开药，只有疑难杂症（模糊信号）才转诊。既快又省钱，还不耽误真正需要专家的 case。

## 亮点 2：多策略切块引擎（策略自动推荐 + Parent-Child 双层管道）

### 问题背景

文档解析完了，有了结构树和纯文本，接下来要切成块（chunk）才能向量化入库。但不同文档的最优切法完全不同：
- 一份结构严谨的技术规格书，按章节切最好——每个章节就是一个完整的语义单元
- 一篇散文或博客，没有明显结构，得用递归固定窗口切
- 一份产品白皮书，段落之间有逻辑关系，用语义相似度切能保持连贯
- 一份 OCR 扫描件转出来的脏文本，格式混乱，甚至要靠 LLM 理解语义边界

如果用同一种策略切所有文档，一定会出问题——结构化文档被固定窗口拦腰截断，级别关系丢光；无结构文档用章节切，切出来可能只有一个块（因为找不到标题）。

### 如果不管

所有文档统一 RecursiveCharacterTextSplitter（chunk_size=1000, overlap=200）——这是最常见的做法，也是大多数 Demo 的做法。短期看不出问题，但用户上传一份有 50 个条款的合同之后，搜"第 35 条 违约责任"召回来的 chunk 可能是第 34 条的后半段 + 第 35 条的前半段 + 第 36 条的开头——恰好窗口切在了中间。LLM 看到的证据残破不全，回答质量断崖式下降。

### 我的方案

做了一套策略推荐引擎 + 双层管道执行框架。

**策略推荐（Recommendation）**

解析完成后，文档已经有了结构层级数（structureLevel）、内容质量评分（contentQuality）、段落数和总字数。基于这三个维度的组合做决策：

- **Parent 管道（只跑一步）**：如果文档结构化程度高（structureLevel ≥ 2 或标题数 ≥ 2）→ 用 STRUCTURE 策略按章节收集子树文本；否则 → 用 RECURSIVE 策略递归固定窗口切
- **Child 管道（1-2 步组合）**：如果文档内容质量低但文本量够（低质量 + contentQuality ≥ 1）→ LLM 策略 + RECURSIVE 兜底；如果文档够长且质量不错（≥ 1000 字 + ≥ 3 段 + contentQuality ≥ 3）→ SEMANTIC 策略 + RECURSIVE 兜底；否则 → RECURSIVE only

每步有角色：第一步是 PRIMARY（产出的结果替换初始文本）、中间步是 OPTIMIZE（对上一步结果做合并/拆分优化）、最后一步是 FALLBACK（只有前面全空才执行，保证有兜底）。

**Parent-Child 双层切割**

这是为了解决"既要又要"的问题——既要块够大保留完整上下文（Parent 层），又要块够细让检索精准定位（Child 层）。

- Parent 管道先在结构树层面切出大纲块（比如一章一个 ParentBlock）
- Child 管道在每个 Parent 块内部做精细切分
- Child 继承 Parent 的元数据：sectionPath（"1.2.3"）、structureNodeId、canonicalPath
- 检索时先召回 Child chunk，然后通过父块提升把文本替换成 Parent 块的上下文

**四种策略详解**

| 策略 | 核心逻辑 | 适用场景 |
|------|---------|---------|
| STRUCTURE | 遍历结构树，收集每个 CHAPTER 节点的子树文本。第一章的内容归一个 ParentBlock，第二章归另一个 | 结构化文档（合同、规格书、论文） |
| RECURSIVE | 3 级递归：段落 → 句子 → 固定窗口（3000 字 + 200 字重叠） | 无结构文档、兜底策略 |
| SEMANTIC | 句子级 Jaccard 相似度（1-2 gram tokenizer），相似度低于 0.7 就切一刀 | 长文本、逻辑连贯的白皮书 |
| LLM | 把文本按句子编号后发给 LLM，让 LLM 返回切分点索引。LLM 失败回退 RECURSIVE | 脏文本、OCR 结果、需要语义理解的边界 |

### 核心细节

- 为什么 Child 管道配 RECURSIVE 兜底？因为 SEMANTIC 和 LLM 都可能失败——语义切在短文本上效果差（句子太少，相似度计算不稳定），LLM 可能超时或格式错误。RECURSIVE 是确定性算法，永远能产出结果
- 为什么 LLM 策略只在低质量文档用？因为高质量文档用 STRUCTURE 或 SEMANTIC 就够了，LLM 策略的强项是"理解糟糕格式中的语义边界"——这在脏文档上才有价值。成本也更高，没必要在清晰文档上用
- Jaccard 相似度 1-2 gram tokenizer 怎么理解？中文分词后，"违约责任由甲方承担"切成 ["违约","约责","责任","任由","由甲","甲方","方承","承担"]，两条相邻句子的这些 gram 重叠度低于 70%，说明语义发生了转变，适合切一刀

### 效果

- 结构化文档：章节粒度检索，用户搜"第三章"能精准定位到第三章整块内容
- 无结构文档：语义切块保持段落连贯，不会在句子中间拦腰截断
- 兜底可靠：无论什么策略失败，RECURSIVE 永远垫底保底

### 如果面试官追问

> "为什么不用 LangChain 的 RecursiveCharacterTextSplitter 直接搞定？"

它解决的是通用场景，我说的是企业知识库场景——文档类型高度异构。一份合同和一篇技术博客用同一套参数切，必有一方效果差。策略推荐做的就是把"选择切法"这个决策自动化，而不是让用户或者开发者去手工调 chunk_size。另一个关键差异是 Parent-Child——LangChain 也有 ParentDocumentRetriever，但它的 Parent 也是固定窗口切出来的"更大的固定窗口"，我这个的 Parent 是结构树节点——第一章和第二章的边界是语义边界，不是字符数边界。

## 亮点 3：双通道混合检索 + RRF 融合 + 父块提升 + Rerank

### 问题背景

RAG 检索有一个经典问题：用户问"怎么配置防火墙规则"，向量检索可能召回"防火墙上架指南"（语义相近但完全不相关），关键词检索可能漏掉"安全组配置"（说法不同但意思完全一样）。单通道各有盲区，两个通道的盲区还恰好互补——向量泛但"通人性"，关键词窄但"精准"。

### 如果不管

只用向量检索——用户搜专业术语时召回一堆"读起来像但不是"的内容，LLM 被灌了一堆噪音生成幻觉。只用关键词检索——用户换个说法就搜不到，覆盖不全。

### 我的方案

9 个阶段的完整检索管线，每个阶段都有降级策略：

**Stage 1-2：改写**

先对查询做轻量改写（用 LLM，短查询跳过），把口语化问题转成检索友好的形式。比如"这玩意儿怎么配置"改写为"如何配置防火墙规则"。改写失败不阻塞，用原问题继续。

**Stage 3-4：双通道并行 + 各自超时**

向量通道（PGVector cosine distance）和关键词通道（ES BM25）同时启动，各给 5 秒超时。哪个超时了或失败了就返回空列表，不等它。这样即使 ES 挂了，向量通道还能独立工作。

**Stage 5：证据门控**

两个通道各自有质量门槛。向量通道要求 cosine similarity ≥ 0.45（绝对阈值），关键词通道要求分数 ≥ 通道最高分的 35%（相对阈值）。为什么要两个不同的阈值策略？因为向量相似度是可比较的绝对值（cosine 的数学含义明确），而 BM25 分数是相对值（受文档长度、词频影响，不同查询间不可比），用绝对阈值不如用相对阈值合理。

**Stage 6：RRF 融合**

公式：`RRF_score(d) = Σ 1/(k + rank_c(d))`，k=60，rank 从 1 开始。

为什么要 RRF 而不是简单的分数加权？因为两个通道的分数量纲完全不同——向量是 [0,1] 的相似度，BM25 可以是 0 到几十——直接加权需要归一化，而归一化本身就带有假设。RRF 只关心排名不关心绝对分数，消除了量纲问题。

同一 chunk 出现在两个通道 → source 标记为 "hybrid"，互相印证，排序会自然靠前。

**Stage 7：父块提升**

这一步很关键。检索召回的是 Child chunk（细粒度），但送给 LLM 回答问题时需要足够的上下文。通过 chunk 的 parentBlockId 去 MySQL 查出 ParentBlock 的完整文本，替换掉 chunk 的片段文本。

同时按 parentBlockId 去重——同一个 Parent 块下的多个 Child 都被召回了，只保留分数最高的那个，避免 LLM 看到重复内容。

**Stage 8：Rerank（可选）**

送 Cross-Encoder 模型（SiliconFlow BAAI/bge-reranker-v2-m3）精排。为什么要 Rerank？向量检索和 BM25 都是双塔模型——query 和 document 分别编码，交互发生在最后一层点积。Cross-Encoder 把 query 和 document 拼起来一起编码，全层交互，判断更准。缺点就是慢——这就是为什么只对 Top-K 结果做 Rerank，不是全量。

这一步默认关闭（rerank.enabled=false），因为调外部 API 有延迟和成本。异常时跳过不影响主流程。

**Stage 9：截断 Top-K**

### 核心细节

- 通道超时为什么是 5 秒？因为用户等太久体验差，而且一个通道慢了另一个通道的结果可能已经够用了。RRF 融合对缺失通道有天然容错——单通道结果也能正常工作，只是没有 "hybrid" 标记
- 证据门控的阈值怎么定的？0.45 的向量阈值来自观察——低于这个值的 cosine 相似度，人工抽查发现基本都是噪音。35% 的 BM25 相对阈值，保证不被一个极高分的文档吸走全部名额
- RRF 的 k=60 来自论文的实验值，较大的 k 让排名差异的影响更平滑——就是说排第 1 和排第 2 的差异比排第 10 和排第 11 的差异更显著

### 效果

- 向量通道的语义泛化 + 关键词通道的精确匹配互相补充
- 任一通道故障不影响整体（空列表继续走）
- 父块提升解决了 chunk 碎片化导致的上下文断裂
- Rerank 在成本允许时进一步提升精度

### 如果面试官追问

> "为什么要自己实现而不是用 LangChain/Milvus 的检索？"

核心原因是控制力——我需要知道每一步发生了什么，每个阈值是什么含义。LangChain 的 Retriever 是一个黑盒，你想在 RRf 融合之后加一个父块提升步骤，或者想对关键词通道和向量通道用不同的门控策略，框架层面做不到。自己实现管线虽然代码多，但每一步都可观测、可调试、可独立启停。另一个原因是代价——这个系统已经有 PGVector 和 ES 了，再加一个 Milvus 增加运维复杂度，PGVector 作为 PostgreSQL 扩展完全能满足需求。

## 亮点 4：意图路由引擎（7 级规则 + LLM 回退）

### 问题背景

用户问的问题类型差异很大："第三章讲了什么""第 5 步怎么操作""怎么理解合同里的免责条款"。这三种问法需要完全不同的处理路径：
- 第一种是结构查询——直接用图遍历返回章节内容就行，不需要检索
- 第二种是条目引用——需要先在图里定位到具体条目，再在条目范围内检索
- 第三种是语义检索——需要在全文档范围内找相关证据，然后生成回答

如果所有问题都无差别走 RAG 检索，结构查询也要跑一遍完整的检索管线（改写→双通道→RRF→父块提升→Rerank→生成），延迟高、成本高，而且返回的 chunk 可能还不如直接返回章节结构清晰。

### 如果不管

所有问题走同一条路径——简单结构查询也要几百毫秒检索 + LLM 生成，用户体验差。更糟的是，结构查询的答案往往是确定性的（"第三章第 2 节"），但 RAG 检索可能因为 ranking 波动返回不同结果，每次回答不一样，用户会觉得系统不可靠。

### 我的方案

两层意图判别：规则引擎（覆盖 80% 常见问法）+ LLM 回退（覆盖剩下的 20%）。

**7 级规则引擎（从高到低匹配）**

| 优先级 | 触发条件 | 判定动作 | 置信度 | 示例 |
|--------|---------|---------|--------|------|
| P1 | 邻接关键词命中（"上一节/下一节/前后章节"） | ADJACENCY_LOOKUP | 1.0 | "下一节是什么" |
| P2 | 章节编码 + 方向词（`1.2.3` + "上面/之后"） | ADJACENCY_LOOKUP | 0.92 | "3.2 之后是哪一节" |
| P3 | 引号标题 + 方向词（`"违约责任"` + "下一节"） | ADJACENCY_LOOKUP | 0.90 | "违约责任"下一节 |
| P4 | 结构对象 + 邻接词（"章节" + "前一个"） | ADJACENCY_LOOKUP | 0.86 | "这个章节前面是哪个" |
| P5 | 大纲关键词（"目录/大纲/有哪些章节"） | CHILD_DESCEND | 1.0 | "第三章有哪些小节" |
| P6 | 结构对象 + 大纲动作（"章节" + "列出"） | CHILD_DESCEND | 0.86 | "列出这个条款的子条款" |
| P7 | 条目关键词 + 非强分析（"第几步/第几条"） | ITEM_REFERENCE | 0.80 | "第 5 步具体怎么做" |

匹配顺序从上到下——P1 先检查，命中了直接返回，不往下走。因为优先级越高的规则越明确，误判风险越低。

**LLM 回退的触发条件**

只有三个条件同时满足时才调 LLM：
1. 规则引擎全不命中
2. 单子问题（多问题走多轮检索更稳）
3. 有结构导航线索（问题里提到了章节名、编号等——说明用户确实在看文档结构）

LLM 判定 threshold = 0.75——低于这个置信度的直接走纯检索，不硬判。

**章节解析的四级回退**

判定完动作之后，还需要找到具体是哪个章节：
1. **按编码**（`1.2.3` 模式、中文"第三章"）→ 图服务精确查找
2. **ES 导航索引**（四维搜索：主题 + 方面 + 信息需求 + 问题文本）
3. **本地图结构评分**（sectionPath 匹配 100 分 > title 90 分 > anchor 80 分 > content 45 分，排序取最高）
4. **放弃定位**（null）→ 回退到全文档检索

**11 种导航动作 → 4 种执行模式**：

| 动作 | 执行模式 | 原因 |
|------|---------|------|
| ADJACENCY_LOOKUP, CHILD_DESCEND, GRAPH_ONLY | GRAPH_ONLY | 只查结构，不需要检索 |
| ITEM_REFERENCE | GRAPH_THEN_EVIDENCE | 先定位条目，再在条目范围内检索 |
| DIRECT_RETRIEVAL, TOPIC_CONTINUE/SWITCH, FRESH_TOPIC 等 | RETRIEVAL | 全文档检索 |
| (知识路由低置信度) | CLARIFICATION | 反问用户确认意图 |

### 核心细节

- 为什么规则引擎优先级从"邻接查询"开始？因为邻接查询最好判断——"上一节""下一节"这些词几乎没有歧义。如果放到后面，可能被更模糊的规则错误拦截
- 为什么 LLM 阈值设 0.75？设太高（如 0.9）会导致大量回退到纯检索——规则引擎没命中的本来就不多，LLM 再拒掉一批，结构查询就被当文本检索处理了。设太低（如 0.6）会让 LLM 的低质量判定影响路径选择。0.75 是平衡点
- 11 种动作的设计原则：区分"用户想知道结构"和"用户想通过结构找到内容"。前者走 GRAPH_ONLY（快、确定、不走 LLM 生成），后者走 GRAPH_THEN_EVIDENCE 或 RETRIEVAL（需要检索+生成）

### 效果

- 约 80% 的结构类问题走规则直达，不经过检索管线也不经过 LLM 意图判定
- 响应延迟：纯图查询 < 50ms vs 完整检索管线 200-500ms
- 确定性：同样的问题总是走同样的路径，回答一致

### 如果面试官追问

> "为什么不全部用 LLM 做意图分类？"


<｜｜DSML｜｜parameter name="content" string="true">全部送 LLM 有三个实际考虑。第一是延迟——LLM 调用至少 200ms，用户问"下一节是什么"要等半秒才知道要去查图，体验差。第二是不确定——同一个问题 LLM 可能给出不同的分类结果，这在结构查询场景下很致命——用户连续问"下一节""再下一节""再再下一节"，每次路径不一致会导致诡异的结果。第三是成本——每轮对话都多一次 LLM 调用，积少成多。规则引擎虽然维护起来需要人工，但它是确定性的、零延迟的、零成本的。可以把 LLM 想象成"疑难杂症专家"——大部分常见病全科医生（规则引擎）就搞定了，只有拿不准的才转诊。

## 亮点 5：ReAct Agent 稳定性设计（三层防护）

### 问题背景

Agent 模式（开放对话 + 工具调用）的稳定性是落地最大的挑战。核心风险有三个：
- **并发冲突**：用户快速连续发送消息，两轮对话同时操作同一个 Session，出现数据竞争——前一轮刚创建的 Turn 被后一轮覆盖，或者两轮同时写 Checkpoint 导致状态不一致
- **工具调用失败**：Tavily 搜索超时、网络抖动、API 限流——工具调用在 Agent 循环中是关键路径，一次失败如果不重试，整个思考链就断了
- **无限循环**：模型陷入思考-搜索-思考-搜索的循环不出来——ReAct Agent 没有天然的退出机制，需要外部限制

### 如果不管

没租约 → 并发下对话状态乱掉，用户看到"回复了一半突然跳到下一个问题"。没重试 → 工具调用偶发失败导致整轮对话失败，用户要重来一遍。没限制 → 极端情况下模型疯狂调用工具，token 消耗失控，用户等到超时。

### 我的方案

三层防护：

**第一层：Redis 分布式租约（防并发）**

同一会话同一时间只能有一个请求在执行。用 Redis `SET NX PX` 实现（类比分布式锁的互斥语义）：
- `tryAcquire(conversationId)` → Lua 脚本原子操作，SET 成功返回 owner token
- 执行期间每 TTL/3 秒自动续约——防止长对话（Agent 可能跑好几步）持有锁超时被误释放
- 执行结束 `release()` 校验 owner token——不是自己的锁不能释放，防止误删
- 获取失败 → 直接返回错误 Flux（不阻塞、排队，直接告诉前端"上一轮还在处理中"）

**第二层：工具调用重试 + 降级（防抖动）**

三个拦截器链式处理：
- `TavilyToolInputFallbackInterceptor`：如果 Agent 传给工具的查询参数是 null 或空字符串，自动用原始问题填充——防止 Agent 调用了工具但不传参数
- `ToolRetryInterceptor`：2 次重试，指数退避 + 随机 jitter（初始 500ms, 最大 4000ms）。比如第一次重试等 500ms+random(0,250)，第二次等 1000ms+random(0,500)。加 jitter 是为了防止多个请求同时重试形成惊群效应
- `ToolErrorInterceptor`：兜底，把任何未预期的 Exception 包装成 `ToolCallResponse.error()`，让 Agent 循环继续而不是崩溃

**第三层：Hook 限流（防失控）**

Spring AI Alibaba 的 ReactAgent 支持 Hook 机制，在每次模型调用和工具调用前后插入检查逻辑：
- `ModelCallLimitHook`：单轮最多 8 次模型调用（run limit），线程级 40 次。达到上限 → 强制返回 END 信号，Agent 停止思考
- `ToolCallLimitHook`：单轮最多 6 次工具调用（run limit），线程级 30 次。达到上限 → 返回 END
- 并行工具调用上限 4 个——防止 Agent 同时发起大量搜索调用

**Checkpoint 持久化**

Agent 的思考状态通过 `MysqlSaver` 持久化到 MySQL（`graph_thread` + `graph_checkpoint` 两张表）。这意味着：
- Agent 执行中断（服务重启）后可以恢复
- 同一 Thread 内的多轮对话共享状态，不会丢失上下文
- 支持手动 Reset 某个对话的 Agent 状态

### 核心细节

- 为什么 TTL/3 续约而不是 TTL/2？TTL/2 也行，但 TTL/3 更激进地保证不会因为续约失败导致锁被误释放。续约间隔短了浪费的只是几次 Redis 调用，但锁被误释放会导致并发问题
- 为什么工具重试是 2 次而不是 3 次？Agent 循环本身的步数是有限的（6 次工具调用上限），每步重试 2 次意味着最多 18 次实际 HTTP 调用，已经能覆盖偶发抖动。3 次重试会让长 Agent 轮的延迟进一步放大，收益递减
- MysqlSaver 和 Redis 的分工：Redis 管"能不能执行"（运行态租约），MySQL 管"执行了什么"（持久态存档）。职责分离，不会因为 Redis 重启丢失对话存档

### 效果

- 并发安全：同一会话严格串行，无脏写
- 工具调用成功率：2 次重试覆盖 99% 的网络抖动，偶发 API 限流也能自动恢复
- 防失控：单轮模型调用最多 8 次、工具调用 6 次，token 消耗有上限

### 如果面试官追问

> "为什么不用数据库行锁或乐观锁做并发控制？"

数据库锁的问题在于粒度——你需要锁的是"同一会话的整个执行过程"，而不是某一行数据。Agent 执行可能持续数秒（多次模型调用+工具调用），数据库事务不能开这么久。Redis 租约天然适合这种场景：TTL 自动过期防止死锁、续约支持长任务、非阻塞获取失败直接失败而不是等待。

## 亮点 6：知识路由系统（三级层级路由，零 LLM 调用）

### 问题背景

当知识库里的文档数量从几个增长到几十、几百个的时候，每次提问都要先回答一个问题：**应该在哪个文档里找答案？**

最简单的做法是让用户手动选——但几十个文档用户根本记不住哪个文档里有什么。第二个做法是拿用户问题去所有文档做一遍检索，按最高分文档聚合——这能跑，但每次检索要扫几百个文档，延迟和计算成本都高。第三个做法是调 LLM 决策——但 LLM 调用有延迟，而且你还要先告诉 LLM 有哪些文档可选（如果文档很多，上下文窗口可能装不下）。

### 如果不管

全局检索（不指定 documentId）——每次提问扫全库。文档少的时候还好（< 10 个），超过 50 个文档后检索延迟明显上升，而且跨文档的噪音（不同文档里的相似段落）会稀释相关文档里的真正匹配。

### 我的方案

用结构化层级缩小搜索范围——Scope（领域）→ Topic（主题）→ Document（文档）——三层逐级收敛，每层做复合评分而不是 LLM 判定。

**核心思路：逐级剪枝**

```
用户提问："容器化部署的最佳实践"
         │
         ▼
Level 1 — 从 5 个 Scope 中选出 Top 3:
  "基础架构"(0.89) > "DevOps"(0.76) > "安全合规"(0.12) > ...
         │
         ▼ (范围从 5 → 3)
Level 2 — 在 Top 3 Scope 范围内，从 15 个 Topic 中选出 Top 5:
  "K8s部署"(0.91) > "Docker配置"(0.83) > "CI/CD"(0.65) > "监控告警"(0.42) > ...
         │
         ▼ (范围从 15 → 5)
Level 3 — 在 Top 5 Topic 范围内，从 40 个 Document 中选出 Top 3:
  doc-123(0.94) > doc-87(0.71) > doc-205(0.58)
         │
         ▼
     返回 Top 1 Document + 置信度
```

**每层的评分公式（不调 LLM）**

```
score(entity) = semanticScore + lexicalScore + keywordHitScore
               + scopeMatchBoost + relationWeight

semanticScore  = max(0, (cosine(e.embedding, q.embedding) - 0.20) × 50.0)
                  ↑ 语义 floor=0.20——低于这个值的语义分直接归零，防止弱相关性依然给分
lexicalScore   = min(10.0, esBM25Score × 1.6)
                  ↑ 词法 cap=10.0——防止某个文档因为词频异常在 ES 得分过高，单项统治总分
keywordHitScore = matchedTerms × 6.0
                  ↑ 查询词直接命中实体字段（标题、描述、标签）的奖励
scopeMatchBoost = 8.0 (topic 匹配 top scope) 或 15.0 (document 匹配 top scope)
                  ↑ 上级路由结果对下级的加权——scope 选对了，该 scope 下的 topic 和 doc 应该加分
relationWeight  = 分数 × (1 + 20.0)  (Topic-Document 显式关联)
                  ↑ 管理员手动绑定的 topic-document 关系，权重显著高于自动匹配
```

每一层按这个公式评完分后排序截断——Scope 保留 Top 5，Topic 保留 Top 8，Document 保留 Top 5。不是只取 Top 1，因为下一层可能需要备选。

**置信度计算**

最后取 Top 1 和 Top 2 的分差比：
```
confidence = topScore / (topScore + secondScore + max(1, 10/topScore))
```
- 如果 Top 1 0.95, Top 2 0.30 → confidence ≈ 0.95/(0.95+0.30+0.1) ≈ 0.70 (高置信)
- 如果 Top 1 0.80, Top 2 0.78 → confidence ≈ 0.80/(0.80+0.78+0.08) ≈ 0.48 (低置信)

confidence ≥ 0.55 → SUCCESS（自动选中 Top 1 文档）。< 0.55 → LOW_CONFIDENCE（让用户确认）。< 0.45 且无候选 → FAILED（回退 RAG 兜底）。

**影子评估模式**

支持 SHADOW 模式——路由引擎正常运行并记录结果，但不干预文档选择。这是为了在上线自动路由前，先在真实流量上评估准确率。管理员可以在可观测面板看到：这周 1000 次提问中，路由推荐了 850 次，其中 780 次用户手动选的文档和路由推荐一致（命中率 91.7%）。足够自信后再切到 AUTO 模式。

### 核心细节

- semanticFloor=0.20 的含义：cosine 相似度 0.18 的两个向量——在 1024 维空间里几乎是正交的，没有任何语义相关性。设个 floor 就是明确告诉系统"低于这个值的不算语义相关，别硬蹭分"
- lexicalCap=10.0 为什么需要？ES 的 BM25 分数受文档长度、词频、逆文档频率影响，不同实体间不可比。某篇短文档恰好包含所有关键词，BM25 可能到 50 分——不加 cap，它可能仅凭词法就把语义完全不相关的一个文档拱到第一
- 为什么是 Scope → Topic → Document 三层而不是两层？两层（直接 Document）的问题是：文档一多，ES 词法检索的区分度下降。50 个文档都包含"部署"，单靠 BM25 + cosine 很难区分。三层通过 Scope 和 Topic 的语义空间聚拢候选，减少最底层的候选数量

### 效果

- 纯计算评分，零 LLM 调用，毫秒级完成
- 三级剪枝把 100+ 文档的候选空间逐级收敛到 3-5 个
- 影子模式支持上线前的离线评估

### 如果面试官追问

> "这个和 RAG 的检索有什么区别？为什么不直接用 RAG 做文档选择？"

RAG 检索粒度是 chunk，知识路由粒度是 Document。如果直接跑 RAG 检索（不加 documentId 过滤），检索结果会分散在不同文档的 chunk 里，你需要按 documentId 聚合分数再比较——这个"检索→聚合→比较"的流程本质上就是一个朴素的知识路由。我的做法把这个逻辑前置了：在上游用一个轻量级的评分机制决定去哪个文档，下游 RAG 检索时直接带 documentId 过滤，减少噪声、减少计算量。而且知识路由的 Scope 和 Topic 层用的是人工维护的实体（有名称、描述、关联关系），比 chunk 文本向量携带更多结构化信息。

## 亮点 7：图导航系统（Neo4j + MySQL 双模，Priority-Fallback 模式）

### 问题背景

文档解析完产出的结构树存在 MySQL 里，但图遍历查询（"当前章节的父章节""下一节""所有子节"）在关系型数据库里写起来很痛苦——要递归 JOIN 或者多次查询，代码里全是 parentNodeId、prevSiblingId 的拼接逻辑。

Neo4j 做图遍历天然适合——`MATCH (a)-[:HAS_CHILD*]->(b)` 就搞定了。但它是个额外中间件，不是所有部署环境都想装。

### 如果不管

只用 MySQL——图查询代码复杂、易出错、性能随深度下降。只用 Neo4j——增加了部署依赖，而且 Neo4j 挂了整个导航功能就不可用。

### 我的方案

`CompositeDocumentStructureGraphService` 标记为 `@Primary`，内部封装了 Neo4j 和 MySQL 两个实现，实现了一套 Priority-Fallback 模式：

**路由决策（per documentId）**

```
1. Neo4j Bean 存在吗？
   └─ 不存在 → 直接用 MySQL（环境中没装 Neo4j）

2. 缓存怎么说的？
   ├─ FALSE → 直接用 MySQL（之前试过 Neo4j，不可用）
   └─ null → 调用 neo4j.isGraphAvailable() 探活
       ├─ 可用 → 缓存 TRUE，用 Neo4j
       └─ 不可用 → 缓存 FALSE，用 MySQL

3. Neo4j 执行成功？
   └─ DocumentException → 回退 MySQL（执行中出错，标记不可用）
```

缓存在 `CompositeGraphAvailabilityCache` 里，`ConcurrentHashMap<Long, Boolean>`，按 documentId 粒度。一个文档的 Neo4j 投影失败了，不影响其他文档走 Neo4j。

**两个实现**

Neo4j 实现：原生 Java Driver（非 Spring Data Neo4j），参数化 Cypher 查询。节点标签 `Section`（ROOT/CHAPTER）和 `Item`（STEP/LIST_ITEM），关系 `HAS_CHILD`、`HAS_ITEM`、`NEXT_SIBLING`。8 个索引在 `@PostConstruct` 时创建，保证查询性能。

MySQL 实现：先把文档全量节点加载到 `ConcurrentHashMap` 里，然后在内存中做 Java Stream 遍历。节点数超过 `cacheNodeThreshold=2000` 的文档，每次直接 DB 查而不缓存（防止内存占用过大）。

**章节评分的多维度设计**

`findBestSection(question)` 的评分权重经过调优：
- sectionPath（如 "1.2.3 系统架构"）匹配问题关键词 → **100 分**
- title 匹配 → **90 分**
- anchorText（锚文本，章节的摘要描述）匹配 → **80 分**
- contentText（章节正文）匹配 → **45 分**
- facet（方面标签）匹配 → **1-5 分**

这个权重设计的逻辑：sectionPath 最精确——包含章节编号，匹配上了几乎可以肯定是对的。title 也很精确。content 匹配虽然语义相关但可能是巧合（正文里提到了另一个章节的术语），所以权重低。

**兄弟节点获取的踩坑经验**

Neo4j 的兄弟关系最初设计用 `NEXT_SIBLING` 关系方向来判断 `previousSibling` 和 `nextSibling`——但 Cypher 中关系的方向性在回退场景下容易出错。最终方案是直接在每个节点上存 `prevSiblingNodeId` 和 `nextSiblingNodeId` 两个字段，建索引后直接查——比遍历关系更稳定。

### 核心细节

- 为什么缓存的粒度是 documentId 而不是全局？一个文档的 Neo4j 投影因为数据问题失败了（比如结构节点有环），不应该影响其他正常文档继续用 Neo4j
- MySQL 实现中 `cacheNodeThreshold=2000` 是怎么定的？一个文档 2000 个结构节点意味着它有 2000 个标题+条目，已经是非常庞大的文档（大概 1000+ 页）。这种文档全量缓存到内存里不划算，每次 DB 直查反而更合理
- 为什么不用 Spring Data Neo4j 而用原生 Driver？控制力。我需要精确控制 Cypher 查询的参数化、超时和错误处理。Spring Data 的 Repository 抽象在这些定制场景下不够灵活

### 效果

- Neo4j 可用时享受图数据库的遍历性能
- Neo4j 不可用时自动降级到 MySQL，用户无感知
- 按文档粒度的缓存，故障隔离

### 如果面试官追问

> "直接用 MySQL 的 Recursive CTE 不也能做图遍历吗？"

能，但有三个实际限制。第一，CTE 写起来复杂——"找某个章节的所有祖先""找某个章节的所有兄弟"这些查询在 Neo4j 里是两三行 Cypher，在 SQL CTE 里是一大段。第二，深度不确定——有的文档只有 3 级标题，有的有 8 级，CTE 需要处理可变深度。第三，混合查询——"找第 5 步的父章节的所有子章节"这种跨关系类型的查询在 Neo4j 里是自然的图遍历，在 SQL 里要多次 JOIN，可读性和维护性都差。Neo4j 的正确用法是：不把它当主存储（主存储还是 MySQL），只把图遍历那部分给它做。

## 亮点 8：全链路可观测性（10 阶段追踪 + P50/P90/P99）

### 问题背景

AI 应用的调试和传统后端完全不同。传统后端报个 500，你看堆栈就知道哪里错了。AI 应用的问题是"回答质量差"——你完全不知道是检索召回了噪音？是改写把问题改偏了？是 LLM 生成时幻觉了？还是记忆上下文带偏了方向？每个环节都可能出问题，但出问题时你没有任何线索。

### 如果不管

用户反馈"回答不太对"，开发只能靠感觉猜——"可能是检索没召回？可能是 LLM 问题？"——然后去查日志大海捞针。没有量化指标，优化也无从下手。

### 我的方案

每一轮对话打 10 个追踪点，每个点记录开始时间、结束时间、成功/失败状态、耗时、关键详情。

**10 个阶段的含义和可发现的问题**

| 阶段 | 记录内容 | 能发现什么问题 |
|------|---------|--------------|
| MEMORY | 加载耗时、近期轮数、摘要长度 | 记忆加载慢（DB 查询问题）、摘要过长消耗 context |
| INTENT | 意图分类结果、confidence | 规则引擎误判（该走图的走了检索） |
| REWRITE | 改写前后文本、多问题拆分结果 | 改写偏了方向、该拆没拆、不该拆拆了 |
| ROUTE | 路由路径、候选文档、置信度 | 选错了文档、LOW_CONFIDENCE 频率高 |
| RAG_RETRIEVE | 双通道各自耗时、召回数、各通道分数分布 | 某通道超时、召回不足、门控太松/太紧 |
| EVIDENCE_BUDGET | 证据数量、预算消耗、被截断的内容 | 证据不够、或证据太多超过上下文窗口 |
| ANSWER_GENERATE | LLM 生成耗时、token 消耗、首 token 延迟 | 模型响应慢、token 消耗异常 |
| REACT_AGENT | 工具调用次数、每步耗时、终止原因 | 循环次数过多、某工具调用特别慢 |
| RECOMMENDATION | 追问生成耗时、生成数量 | 追问生成失败或质量差 |
| FINALIZE | 持久化耗时 | 归档写入慢 |

**Model Usage 自动追踪**

每次 LLM 调用（无论是改写、Agent 思考、答案生成、追问推荐）都通过 `ObservedChatModelService` 自动记录：
- `stageName`：在哪个阶段调的
- `provider` + `model`：DeepSeek/通义千问、具体模型名
- `promptTokens` + `completionTokens`：输入输出 token 数
- `cost`：根据 `ChatProperties.Pricing` 配置的单价自动计算
- `durationMs`：调用耗时
- `status`：SUCCESS / ERROR / CANCELLED

**聚合查询**

`ChatStageBenchmarkService` 从追踪数据计算各阶段的 P50/P90/P99 延迟。这可以回答：
- "用户的平均等待时间是多少？瓶颈在哪？"
- "P99 和 P50 差距大不大？是不是有长尾？"

### 核心细节

- 追踪不是事后分析——它在每轮对话执行时同步记录，异常时也能看到最后的状态
- `ChatTraceRecorder` 是每轮一个实例，天然隔离不同轮次的追踪数据
- 成本计算不是猜的——按模型的实际 pricing 配置，`perKTokenCost` map 用模型名前缀匹配。所以 DeepSeek-V3 和 DeepSeek-R1 可以配不同的价格

### 效果

- 回答质量下降时可以快速定位瓶颈（检索？改写？生成？）
- P50/P90/P99 延迟量化，优化有数据支撑
- 成本可追踪到每个对话轮次

### 如果面试官追问

> "这和 OpenTelemetry 有什么区别？为什么不直接用现成的？"

OpenTelemetry 解决的是通用分布式追踪（Span 之间的调用链），我这个解决的是 AI 管线的领域追踪——每个阶段要记录的不是"调用了哪个服务"，而是"改写前后的文本变化""检索的分数分布""LLM 的 token 消耗"。这些领域数据在通用 Tracing 系统里只能以 attribute 形式塞进 Span，查询和分析都不方便。自己实现追踪系统的成本并不高（几个表 + 一个 Recorder），但赋予了领域语义——团队看 P90 的 RAG_RETRIEVE 延迟就知道检索层是不是该优化了，而不是从一堆 Span 里手动拼。

## 综合：如果面试官问"这个项目你最大的收获是什么"

> 我以前写代码是被"需求驱"的——PM 说什么做什么。这个项目从头到尾我一个人设计，逼着我去想"为什么"。比如文档切块——市面上都在用 RecursiveCharacterTextSplitter，同事和教程都告诉你 chunk_size=1000, overlap=200。我不满足于"大家都这么用"，而是去实验不同的切法在不同文档上的效果，最后发现一刀切就是不行——结构化文档和非结构化文档需要的是完全不同的策略。再比如 RAG 的 RRF 融合——论文里写的公式，大部分实现照搬，但我在实现时发现向量和 BM25 的分数量纲差异如果不处理，直接加权就是错的。
>
> 这个项目让我从一个"会用工具的人"变成了"能判断什么时候不该用某个工具的人"。
